PH60-Multi V2 stability candidate — 2026-10-19

Target: ph_lite + PH60-Multi_V2, existing HHKB keymap, Studio enabled and locked.
This candidate addresses several reproducible paths that can lose a release;
the cause of the intermittent issue on the user's keyboard is not yet proven.

The default Build ZMK firmware workflow calls .github/workflows/ble-recovery.yml.
It applies the patch and runs tests before compiling the patched variants.
Artifacts:
  Stability: patched firmware, recommended for the first on-device trial.
  Baseline: original board configuration and unpatched ZMK, for comparison/rollback.
  Stability_Debug: the same fixes with USB logging for diagnosis.
These are normal application UF2 files, not settings-reset images.

Changes:
  - Keep keyboard and consumer reports in order across failed BLE sends, tied
    to their original connection. Retry every 20 ms; request a disconnect after
    4 s of persistent failure (matching the 4000 ms BLE supervision timeout) so
    short RF stalls can recover without prematurely disconnecting and discarding
    a pending key-up report. If disconnect also fails, retain the report for
    retry. Use encrypted HID value attributes.
  - Allow the host 5 s rather than 1 s to become ready for reports (encrypted,
    subscribed and change-aware: -EPERM/-EINVAL/-EAGAIN otherwise). A link still
    not ready after that is ended, so the host can reconnect instead of losing
    every report. The 4 s disconnect applies to other send failures, timed from
    when the host was last not ready.
  - Clear local HID keyboard/consumer/mouse state immediately when BLE
    disconnects while staying on the same profile (when USB is not ready), so
    stale pressed key bits cannot persist across reconnects.
  - Detect outstanding sends with no progress, including a blocked send call.
    Normal held keys have no pending report after their press is accepted;
    there is no forced key-release timer and normal long holds remain supported.
  - Enlarge the scan queue to 75. On overflow, drain ordered events then reconcile
    the latest physical state through the normal position event path. A complete
    very short tap during overflow can still be lost, but a final release is
    no longer silently discarded. Layout changes require a quiescent keyboard.
  - Retry advertising after temporary Bluetooth resource errors, including
    controller memory shortages reported as -EIO, with bounded backoff, using
    the latest selected profile.
  - Backport upstream Studio combo settings finalization (c61fe0b / 8fb6209) so
    reserved Studio combo slots initialize cleanly on boot and reload.
  - Update PH60-Multi_V2.conf matrix and BLE stack settings: increase debounce
    press to 5 ms and add 10 us column-to-row settle delays to eliminate col2row
    diode RC discharge crosstalk; enlarge heap (32 KB), system workqueue stack
    (4 KB), HOG BLE thread stack (2 KB), Studio RPC stack (8 KB), and L2CAP/ACL
    TX buffers (10); restore 2M PHY, reduce peripheral preferred latency to 6,
    and allow 500 ppm LFCLK tolerance.
Keymap is unchanged.

Each artifact includes its config commit, frozen dependency manifest, effective
Kconfig and SHA-256 checksum. Both the default workflow and direct builds use
the same local reusable workflow. Baseline intentionally omits the patch and
restores the original board configuration. build.yaml is the legacy matrix;
the active Multi V2 matrix is in .github/workflows/ble-recovery.yml.

Validation:
  Host fault-injection tests compile the production C fragments using mock
  Zephyr/Bluetooth APIs, with AddressSanitizer and UndefinedBehaviorSanitizer.
  They cover failures, queue overflow, profile changes, reconnection, normal
  holds and watchdog progress. They do not simulate the radio or kernel fully.
  GitHub Actions compiles the complete firmware for all three artifact variants.
  Hardware testing is still required; successful compilation is not proof that
  the intermittent symptom is eliminated.

On-device trial:
  1. Keep the Baseline UF2 for rollback. Flash Stability using the keyboard's
     existing UF2 bootloader procedure. Do not run settings-reset or clear bonds
     as part of this initial comparison.
  2. Check normal typing, held letters/backspace/arrows, modifiers and layers,
     media keys, Bluetooth profile switching, sleep/wake and USB operation.
  3. If repetition returns, record the time, whether another key stops it,
     whether the keyboard disconnects/reconnects, and whether USB is affected.
     Use Stability_Debug for a subsequent diagnostic run if needed.
  4. Reflash Baseline if the candidate introduces a regression. Existing stored
     settings can override the compiled default keymap in all three builds.
